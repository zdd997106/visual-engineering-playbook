# 哪些事可以自己改？

同樣是「寄送邀請」這顆按鈕，改提示文字、改全站按鈕的間距、改誰能寄邀請，會影響不同的人。你可以先用這張表判斷。

| 想改什麼 | 誰做決定、怎麼確認 |
| --- | --- |
| 一般成員看不懂按鈕為什麼是灰色的 | 你可以改提示文字、位置和出現時機，請 AI 準備一般成員與管理員的畫面讓你對照。 |
| 所有按鈕的圖示都太靠近文字 | 你可以調整共用元件。先看有哪些頁面會跟著變，再一起驗收。[怎麼試共用元件](#一個畫面還是每個畫面都要改) |
| 一般成員也應該能寄出邀請 | 這會改變邀請權限。請 AI 整理目前的限制和你的需求，交給工程師確認。 |
| 想看寄送失敗後重試會怎樣 | AI 可以模擬失敗，讓你把流程點完。真正的寄信服務由工程師驗證。[Storybook 可以試到哪裡](#在-storybook-能試到哪一步) |

## 一個畫面，還是每個畫面都要改？

如果你覺得邀請表單的按鈕太擠，先說明只想改這個地方。若你想改的是整個產品的按鈕，設計師也可以做這個決定。AI 會找出哪些地方用了同一個元件，挑幾個實際畫面給你試。

```text
請用 $design-with-storybook 幫我把共用按鈕裡的文字和圖示拉開一點。先讓我看看短文字、長文字，
還有放在窄欄位裡的按鈕，用這個間距會長什麼樣子。
```

顏色、字級和間距也常由多個畫面共用，這種設計值叫 **design token**。例如你想調淡輔助文字，就可以把淺色卡片裡的日期、深色側欄裡的說明放在一起看，再決定要改共用顏色，還是只改卡片。若最後改了共用元件或 token，AI 會在 PR 裡寫清楚哪些地方會跟著變。

## 在 Storybook 能試到哪一步？

你想看送出成功後的下一頁，手邊卻沒有測試資料，AI 可以用產品的頁面配上模擬回應，讓你從送出一路點到結果。你在這裡能確認提示看不看得懂、下一步好不好找。邀請信有沒有真的寄出、資料有沒有寫進系統，交給工程師驗證。

有時光是開啟邀請表單就得取得真實的登入身分。如果 AI 找不到能在本機模擬這段行為的地方，可以請它把問題整理給工程師。

```text
我想看一般成員開啟邀請表單時的權限提示。如果目前只能連到真正的登入服務，
請幫我寫一段給工程師的說明，告訴他我想試哪個畫面、卡在哪裡。
```

工程師可以協助讓這個畫面讀取模擬的權限，讓你在 Storybook 裡看到一般成員會看到的提示。產品裡誰有權寄邀請，仍沿用原本的規則。你已經試過的其他調整也可以先保留。

## 回來繼續做的時候

**昨天的預覽跟今天的產品對不上。** 告訴 AI 你要繼續哪個畫面。若另開了對話，記得再點名 `$design-with-storybook`。它會回到原來的分支，比對現有元件，必要時重建這個任務用的 Story。團隊共用的 Story 和其他任務各自保留。

**畫面看起來對，檢查卻沒過。** AI 會查原因，說明這項檢查和你改的地方有沒有關係。如果修正後畫面有變，它會再給你連結。碰到產品規則的問題，就請工程師接手。

**只改了前端，存成 commit 或推送時卻說缺少後端工具。** 有些專案會一起檢查前端和後端。工具齊全時，AI 會照常跑。假如你只改了按鈕文字，卡住的是跟這次修改無關的後端測試，AI 會告訴你少了什麼工具、其他哪些檢查還會跑，再問你能不能略過這項測試。

你同意後，在同一個對話裡繼續改這個專案，遇到相同情況就不用再答一次。每次儲存或推送，AI 都會針對當次修改照跑該做的前端和安全檢查。如果這些檢查沒過，AI 會先處理。換了對話，或推送時遇到先前沒談過的檢查，就要重新確認。

**工程師在 PR 留了意見。** 把那則留言交給 AI，它會接著在原本的分支上改。如果連操作方式都變了，你會先看到新版畫面。你接受修改後，AI 會存到本機。下次要推送時，它會先列出新增的修改和要更新的 PR，等你同意才送出。
